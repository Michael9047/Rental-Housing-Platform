- 刷新或切换历史会话后，新的历史回复可以恢复完整房源卡、状态 chips、FAQ 跳转，而不只是恢复纯文字。

## 二、问题根因

### 1. 多轮记忆和“这个”失效

旧链路主要把最近几条聊天文本重新交给模型，没有持久化以下结构化数据：

- 当前有效筛选条件；
- 上一轮候选房源顺序；
- 上一轮第一套房源和最后聚焦房源；
- 用户明确保存、希望跨新会话使用的长期偏好。

因此“你推荐的这个有健身房吗”容易被误判成一次新的全局设施搜索，“这几套哪个好”也可能退回购物车或重新召回不相关房源。

### 2. 楼内设施和楼外周边概念混用

原逻辑可能把 UnitType/Institute 的 `amenities` 当成周边 POI。楼内有自习室，只能证明公寓内部有自习空间，不能证明楼外附近存在图书馆、共享办公或独立自习室。

### 3. NUS 结果混入其他国家

学校缩写没有稳定补齐国家硬条件。模型漏提 NUS 时，查询可能只剩 `studio`，宽召回就会混入 UCL、UCLA 或香港房源。

### 4. 搜索页 Agent 缺少当前页面上下文

旧搜索页没有稳定传递当前筛选条件和当前结果 ID。“这几套”无法知道用户指的是页面上的哪几套；最初实现只传前 5 套，又造成页面有 6 套但只比较 5 套。

### 5. 长内容无法发送

后端消息 schema 原上限为 4,000 字，前端也是单次普通请求。长需求会被限制、截断或因等待完整长回复而表现为失败。

### 6. Agent 会话和客服会话未隔离

两类会话共用 `chat_sessions`，但以前没有 `session_kind`。Agent 历史记录无法可靠列出、恢复和隔离。

## 六、数据库迁移说明

当前代码迁移 head 为 `20260802_0101`。新代码上线前需要对应的 `session_kind` 列和 4 张 Agent 表，否则会因缺列/缺表失败。

但本机原开发库的 `alembic_version` 停在 `20260722_0019`，真实表结构又包含部分后续字段，属于“迁移记录和真实结构漂移”。直接对原开发库执行 `alembic upgrade head` 会在重复字段处失败，而且中间历史迁移包含高风险数据处理。因此本次没有继续升级原开发库，而是使用隔离验证库验收。

上线或处理原开发库前应：

1. 先备份数据库。
2. 对照 `20260722_0019` 到 `20260725_0100` 的每个迁移检查真实表结构。
3. 用补偿迁移或经过确认的 `stamp` 对齐版本，不能直接盲目升级。
4. 再应用 `20260802_0101`。

此外：

- downgrade 会删除 Agent 状态、长期记忆和搜索审计表，降级前必须备份。
- 搜索审计会持续增长，应在上线前补充保留期、脱敏和容量监控。
- 迁移中的 `session_kind` 旧数据回填依赖旧标题，生产数据应抽查。

## 七、仍需遵守的事实边界

1. 当前能确认楼内/公寓自习室；没有 POI 数据时不能确认楼外附近的独立自习空间。
2. 合同、押金、退款等 FAQ 目前是占位政策，正式上线前需由业务方确认文本。
3. 新产生的历史回复会保存完整推荐卡；修复前已经存下、只有 ID/分数的旧历史消息无法自动补回当时所有卡片字段。
4. 20,000 字是接收上限；检索 embedding 和历史上下文仍会按各自预算压缩，不代表全部 20,000 字进入每一个模型步骤。
5. 高频学校确定性词典目前覆盖 NUS、NTU、UCLA、UCL、LSE、HKU；其他学校依赖数据库或模型识别。
