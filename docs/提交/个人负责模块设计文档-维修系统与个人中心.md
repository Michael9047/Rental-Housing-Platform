## 一、模块概述

### 1. 模块功能简介

本设计文档覆盖两个模块：

- **维修系统**：租客对已预订/入住房源提交报修工单，系统自动流转给对应公寓的 **BD（Business Manager）** 处理。支持严重程度分级（低/中/高）、公寓联系人展示、租客确认/驳回（必填原因）、处理记录与维修照片。维修工（maintenance_worker）与房东旧流程**入口已隐藏**，代码保留但不再作为主要参与方。
- **个人中心**：租客登录后查看自己的**合同、账单/订单、租客档案、账号设置**。合同/订单平铺展示、状态显示在卡片右上角、点击卡片进入详情；修复「预订状态」显示逻辑，使预订状态与支付状态解耦。

### 2. 模块设计目的

- 维修系统：简化报修流转，**报修直达 BD**，去掉「房东是否有维修工」的复杂判断，让工单第一时间到能处理的人手里；通过严重程度分级和公寓联系人，提升处理效率与信息透明度。
- 个人中心：把租客的合同、订单、档案集中管理，方便租客随时查看进度、签约、支付；修复三层架构迁移后个人中心页面无法正常显示合同/订单的问题。

### 3. 依赖模块/前置条件

| 依赖 | 说明 |
|------|------|
| auth / user | 登录认证、角色（tenant / bd_manager / admin / maintenance_worker / landlord） |
| property / institute / unit_type | 房源三层架构（公寓 → 户型），报修关联的房源与公寓联系人 |
| booking | 预约/预订，报修弹窗的「房源」下拉数据来源 |
| contract | 合同生成/签署/快照，个人中心「我的合同」 |
| payment | 支付订单，个人中心「我的账单/订单」 |
| tenant | 租客档案，个人中心「我的信息」 |
| notification | 报修通知（BD 收到新报修、高严重度额外通知 Admin、租客收到完成/驳回通知） |
| uploads / images | 报修图片、完成维修照片上传 |

### 4. 模块适用场景

- 租客入住后房屋出现水电、家电、门窗等故障 → 在个人中心「报修」Tab 提交报修，选择房源与严重程度。
- BD 收到报修通知 → 在「报修管理」（BdRepairs）查看所有工单，开始处理、标记完成并填写处理记录。
- 租客查看维修结果 → 确认修好（终态）或填写原因驳回（工单回到处理中）。
- 租客查看自己的电子合同、待支付/已支付订单、租客档案，进行签约、支付、资料维护。

## 二、功能需求说明

### 2.1 核心功能列表

#### 维修系统

- 功能1：**报修创建**——租客选择房源、问题类型、严重程度（低/中/高）、描述、可选预约时间与图片，提交后自动通知所有 BD（高严重度额外通知 Admin 兜底）。
- 功能2：**报修列表/详情**——租客看自己的工单，BD/Admin 看全部工单；详情含房源、公寓联系人电话、严重程度、处理记录、驳回原因、维修照片。
- 功能3：**BD 处理**——BD「开始处理」（→ in_progress）、「标记完成」并填写处理记录、可附维修照片（→ completed）。
- 功能4：**租客确认/驳回**——租客确认修好（→ confirmed 终态）；或填必填原因驳回（→ 回到 in_progress，重新处理）。
- 功能5：**取消报修**——租客可取消 pending 状态下的报修（→ cancelled）。
- 功能6：**隐藏维修工与旧房东流程**——maintenance_worker 角色的工单中心/维修师傅管理/维修工看板入口隐藏；房东派单/审核旧流程不再作为主流程；Admin「待派单工单」「房东维修工看板」入口隐藏。代码保留不删，仅隐藏入口。
- 功能7：**维修工体系（原架构，入口已隐藏、代码保留）**——原设计为「房东 + 维修工」模式：租客报修后自动检测房东名下是否有维修工（`RepairWorker.scope = apartment`），有则工单为 `pending` 并通知房东，无则工单为 `pending_escalated`（待后台派单）并通知 Admin；房东负责派单（`assign_worker`，检查维修工状态 `available`）与审核；维修工在「工单中心」开始工作（`start_work`）→ 完成并填维修记录（`complete_work`）；租客确认修好（`confirm_repair`，更新维修工评分）。对应 `RepairWorker` 模型、`repair_workers` 路由、`WorkerManagement/WorkerOrders/WorkerDashboard` 页面、`require_maintenance` 依赖——本次重构后这些入口隐藏，代码与模型全部保留，便于兼容与后续恢复。

#### 个人中心

- 功能1：**合同列表/详情**——展示全部合同（平铺，不做分类筛选），状态显示在卡片右上角，可查看合同正文、下载已签署 PDF。
- 功能2：**账单/订单列表/详情**——展示全部订单（平铺），状态右上角，点击卡片进入订单详情；可继续支付、查看合同、重新预订。
- 功能3：**租客档案管理**——增删改查租客档案、设为默认，作为签约时个人信息的数据源。
- 功能4：**账号设置**——修改密码、更换手机号、微信绑定、通知设置。
- 功能5：**预订状态修复**——「预订状态」只反映预订流程本身（已批准/已支付即成功），与支付是否 webhook 确认解耦，避免已成功订单显示「预订未成功」。

### 2.2 输入输出说明

- **模块输入**：
  - 维修：`property_id`（房源/户型 id）、`issue_type`、`severity`、`description`、可选 `images`/`scheduled_time`；BD 处理动作参数（`work_record`、`work_images`、驳回 `reason`）。
  - 个人中心：当前登录用户（JWT），浏览各 Tab。
- **模块输出**：
  - 维修：`RepairRead`（id、property_id、tenant_id、landlord_id/bm、severity、status、reject_reason、work_record/images、property_title、institute_contact 等）。
  - 个人中心：`TenantContractListItem[]`、`TenantOrderListItem[]`、`TenantProfile[]`、`DashboardSummary`。

### 2.3 业务规则与约束

- **维修状态机**（简化后的闭环）：
  ```
  租客报修 → pending（待处理）
      ↓ BD 开始处理
  in_progress（处理中）
      ↓ BD 标记完成
  completed（待确认）
      ├→ 租客确认 → confirmed（已确认，终态）
      └→ 租客驳回（必填原因）→ 回到 in_progress
  pending → cancelled（租客取消）
  ```
- 角色权限：tenant 只能看/操作自己的工单；bd_manager 可看全部并处理；admin 看全部（高严重度兜底通知）。
- 驳回必须填写原因，否则拒绝操作。
- 只有 `completed` 状态可被确认，只有工单创建者本人可确认/驳回。
- **隐藏内容约束**：maintenance_worker 工单中心、房东派单审核、Admin 待派单/房东看板入口均隐藏，但对应代码、模型、依赖保留（不删除），便于后续恢复或兼容。
- 个人中心订单仅在「存在已签署合同 + 有效房源」时展示；预订状态与支付状态分离展示。

### 2.4 权限矩阵（含隐藏角色）

| 操作 | 租客 tenant | BD (bd_manager) | Admin | 维修工 maintenance_worker（隐藏） | 房东 landlord（隐藏） |
|------|:---:|:---:|:---:|:---:|:---:|
| 创建报修 | ✅ | ❌ | ❌ | ❌ | ❌ |
| 查看列表 | 仅自己的 | 全部 | 全部 | 仅分派给自己的 | 仅自己的 |
| 查看详情 | 仅本人 | 全部 | 全部 | 仅分派给自己的 | 仅本人 |
| 开始处理 | ❌ | ✅ | ❌ | ✅（原架构） | ❌ |
| 标记完成 | ❌ | ✅ | ❌ | ✅（原架构） | ❌ |
| 确认维修 | ✅ 仅本人 | ❌ | ❌ | ❌ | ❌ |

## 三、整体设计思路

### 1. 设计整体架构

采用「三层架构兼容 + 角色权限 + 状态机」：

```
前端（Vue3 + Element Plus）
  ├─ 维修：个人中心「报修」Tab / RepairDetail / BdRepairs（BD端）
  └─ 个人中心：Profile.vue（合同/账单/档案/设置 Tab）
        ↓ axios（/api/v1）
后端（FastAPI）
  ├─ 维修：repairs.py 路由 → RepairService → repair_requests 表
  └─ 个人中心：contracts/payments/tenants/me 路由 → 对应 Service
        ↓ SQLAlchemy async
数据库（PostgreSQL + pgvector）
  ├─ 三层架构：institutes → unit_types → bookings
  └─ 业务表：repair_requests、contracts、payments、tenants…
```

- **兼容层**：模型层同时兼容旧字段（`property_id`/`landlord_id`）与新字段（`unit_type_id`/`bm_id`），读取时用新列填充旧列，保证旧前端/旧代码不报错。
- **角色门控**：路由层用 `require_tenant` / `require_bd_manager` / `require_admin` 控制权限。

### 2. 核心流程逻辑

- 维修：`租客报修 → 直达BD通知 → BD开始 → BD完成(填记录/照片) → 租客确认/驳回`。
- 个人中心订单/合同：`预订(booking) → 审批(approved) → 生成合同(contract_ready) → 签约(signed) → 创建支付(payment_pending) → 支付成功(paid)`，个人中心按需展示各状态。

### 3. 设计亮点/优化点

- **报修直达 BD**：去掉「检测房东有无维修工」的复杂分支，工单统一 `pending` 后通知所有 BD，简化流转。
- **严重程度分级**：高严重度额外通知 Admin 兜底，避免紧急工单被遗漏。
- **公寓联系人透出**：报修详情直接展示公寓联系人电话（Institute.contact_phone），BD/租客可电话沟通。
- **预订状态与支付解耦**：`reservationLabel()` 只按预订流程判定「预订成功/待确认/未成功」，不再误判已支付订单。
- **三层架构兼容**：模型/服务层统一用 `unit_type_id`/`bm_id`，并对旧字段做兼容填充，前端零侵入。
- **平铺式个人中心**：去掉合同/订单的分类筛选，全部平铺，状态统一右上角，降低理解成本。

### 4. 原架构（有维修工版本）与本次改动的对比

**原架构（房东 + 维修工）**：

```
租客报修 → 后端检测房东名下是否有维修工（RepairWorker.scope = apartment）
  ├─ 有 → pending → 通知房东
  │       → 房东派单（assign_worker，校验维修工 available）→ assigned
  │       → 维修工开始工作（start_work）→ in_progress
  │       → 维修工完成（complete_work，填维修记录）→ completed
  │       → 租客确认（confirm_repair，更新维修工评分）→ confirmed
  └─ 无 → pending_escalated（待后台派单）→ 通知 Admin
          → Admin「待派单工单」分配平台维修工（plat_worker）
```

**本次改动（报修直达 BD）**：

- 去掉「检测房东有无维修工」的分支，工单统一 `pending` 后通知所有 `bd_manager` 直达处理。
- BD 承担原「房东 + 维修工」的处理职责（开始处理/标记完成/填处理记录）。
- 维修工、房东派单、Admin 待派单等原架构入口**隐藏保留**：代码、模型（`RepairWorker`）、页面、依赖均未删除。

## 四、业务流程图

### 维修系统

```

   └→ [租客] 详情 → 驳回（必填原因）→ 回到 in_progress
[pending] [租客] 取消 → cancelled
```

#### 维修系统（原架构 · 有维修工版本，入口已隐藏保留）

```
[租客] 报修
   ↓ 后端检测房东名下是否有维修工（RepairWorker.scope = apartment）
```

### 5.2 实体类/数据模型设计

- `Booking` / `Contract` / `ContractSignature` / `Payment` / `Tenant`：个人中心涉及的核心实体。

核心属性说明：

## 七、核心代码逻辑说明

### 1. 核心算法/核心逻辑

- **报修直达 BD**：`create_repair()` 先查房源（UnitType），取公寓的 `bm_id` 与 `contact_phone`，创建 `RepairStatus.pending` 工单；随后通知所有 `bd_manager`，高严重度额外通知所有 `admin`。
- **预订状态解耦**：`reservationLabel(status)` 工具函数，`pending→待确认`、`rejected/cancelled/payment_expired→预订未成功`、其余（approved/paid/…）→预订成功，不再依赖支付 webhook 是否确认。
- **兼容字段填充**：`BookingService._fill_compat()` 在列表返回前，用 `unit_type_id/bm_id` 填充旧列 `property_id/landlord_id`，避免 `BookingRead` 校验报错、保证报修弹窗房源下拉有值。

### 2. 关键代码块说明

- `repair_service.create_repair`：三层查询（UnitType→Institute→bm_id/contact_phone），建工单，批量通知 BD/Admin。
- `repairs._repair_to_read`：async-safe 组装 `RepairRead`，`property_title` 取 `UnitType.name`，`institute_contact` 取 `Institute.contact_phone`。
- `Profile.vue`：四个 Tab（合同/账单/信息/设置）平铺渲染，订单卡片点击进详情，预订/支付状态标签分离展示。

### 3. 特殊处理逻辑（判空、容错、幂等、并发）

- 房源不存在 / 公寓未配置 BD → 抛 `ValueError`，路由转 400。
- 越权访问（非本人工单 / 非 BD）→ 403。
- 驳回原因必填校验；只有 `completed` 可确认。
- 通知失败用 try/except 包裹，不阻断主流程。
- 列表查询用 `selectinload` 预加载关联，避免 async 环境懒加载报错（greenlet_spawn）。

## 八、异常与容错设计

### 1. 常见异常场景

- 报修选择不存在的房源 / 房源公寓未配置 BD。
- 非本人查看/操作工单、非 BD 处理工单。
- 对非 `completed` 工单确认、驳回原因缺失。
- 数据库缺表/缺列（三层架构迁移导致的字段漂移，如 `unit_type_images`）。
- 个人中心合同/订单关联数据不完整（无已签署合同则订单不展示）。

### 2. 容错处理方案

- 服务层抛业务异常 → 路由层转 HTTP 400/403/404，前端 ElMessage 提示。
- 列表查询对「无合同/无房源」的 booking 直接跳过（`continue`），不中断整页。
- 通知服务异常 try/except 吞掉，仅记日志。
- 缺表/缺列问题通过补齐模型映射 + 建表（`unit_type_images` 等）+ `bootstrap_db.py` 空库建全表解决。

### 3. 日志打印规范

- 使用 `logging.getLogger(__name__)`，关键动作（报修创建、状态变更、通知发送）记 INFO；异常记 ERROR + 堆栈。
- 不打印敏感信息（密码、token）。

## 十、模块难点 & 解决方案

### 1. 开发难点

- **三层架构字段迁移**：模型/服务层新旧字段并存（`property_id/landlord_id` vs `unit_type_id/bm_id`），旧代码直接读旧字段会 500。
- **预订状态与支付耦合**：`booking_is_confirmed` 要求「支付成功 + webhook 确认」，导致已成功订单显示「预订未成功」。
- **缺表/缺列漂移**：模型新增 `unit_type_images` 等表，本地库/历史库缺失，房源查询懒加载直接崩溃。
- **维修旧流程残留**：房东派单/维修工体系入口需隐藏但不删除，避免影响其他模块。

### 2. 对应解决方案

- 模型补 `unit_type_id`/`bm_id` 映射 + 服务层 `_fill_compat` 兼容填充；维修 `create_repair` 直接用 `institute.bm_id` 直达 BD。
- 新增 `reservationLabel()`，预订状态只看预订流程本身，与支付状态解耦。
- 补齐缺失表（`unit_type_images`）、补模型字段（`institutes.bm_id`、`bookings` 兼容列），`bootstrap_db.py` 空库自动建全表。
- 维修工菜单/路由入口隐藏，模型与代码（`RepairWorker`、Worker 页面、`require_maintenance` 依赖）保留，后续可恢复。

## 十二、模块验收标准

1. **功能正常运行**：租客报修 → BD 处理 → 租客确认/驳回全流程可跑通；个人中心合同/订单/档案/设置各 Tab 正常展示与操作。
2. **数据准确无误**：订单金额、合同编号、状态、严重程度、处理记录、驳回原因与数据库一致；预订状态与支付状态区分正确。
3. **异常可正常捕获**：越权、房源不存在、公寓无 BD、驳回缺原因、未登录等场景均有明确提示，不出现 500 白屏。
4. **兼容原有业务**：维修工/房东旧流程代码保留（仅隐藏入口）；旧字段 `property_id/landlord_id` 通过兼容填充继续可用；三层架构新列正常读写，不影响搜索/预订/合同/支付等既有模块。
